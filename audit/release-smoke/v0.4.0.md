## Method

A Python driver pipes JSON-RPC frames into the just-built binary over
stdio, exercising the **whole 20-tool surface** plus the five resource
templates and the server `instructions` block, and prints one line per
assertion. Reads, negative cases and dry-run writes throughout; one
separate reversible probe performed a real write (below).

Run from the same Claude Code session that produced the branch, with the
maintainer monitoring the output live.

## Real-write probes

Reads and dry runs do not exercise the write path: `dry_run` returns
before it sends, so a rundown made entirely of them can be green while
the request marshalling is wrong. Two probes therefore wrote to the live
workspace, each reversible and each verified by an independent read
rather than by the write's own echo.

### Deals — and what it found

The first filled an **empty** field on a single deal (filling empty
destroys nothing and needs no `overwrite`), verified it, then restored
it. It found a defect every unit test had missed: the v2 PATCH path
cannot clear a field. `{"expected_close_date": null}` is rejected
outright (`The value is not a valid 'string'`) and `""` stores the MySQL
zero date `0000-00-00` rather than removing the value. v1's
`PUT /api/v1/deals/{id}` with a null does clear it, which is how we know
this is a v2 gap rather than a Pipedrive-wide one.

The probe's one modified field was restored through that v1 call and the
workspace verified back to its prior shape. The server deliberately does
not reach for v1 here — a third carve-out on an API that sunsets
2026-07-31 — so clearing is documented as unsupported and every optional
input reads "omit to leave it as it is". Evidence:
`docs/architecture.md`, "Clearing a field". This closes the Phase 0
field-clearing spike in `CONTRIBUTING.md`.

### The other four resources

The deal probe left `manage_person`, `manage_organization`,
`manage_activity` and `manage_note` still never having written to
Pipedrive — their PATCH behaviour assumed correct by analogy, which is
exactly the assumption that had just failed. A second probe covered them.

Safety rules, applied to every step: capture the original first, restore
in a `finally` so a mid-probe failure still puts it back, verify the
restore with an independent read, and — for the collection tests — only
ever **append** then remove, so an existing entry is never omitted from a
write and replace-semantics cannot lose data.

Run twice, both times 20/20 with nothing left changed. Three assumptions
the guard machinery rests on are now established rather than assumed:

- **`done: false` really does reopen** a completed activity. The `*bool`
  on `UpdateActivityRequest` was necessary, not defensive.
- **Contact points really do replace wholesale.** The entire
  contact-point guard exists because the schema says so; it is now
  observed.
- **The v1 note PUT works**, and the overwrite guard refuses over real
  populated content, not only against a fake.

It also turned up one thing nobody had written down: changing a person's
`first_name` reports `["name", "first_name"]`, because Pipedrive derives
`name` from the parts, while the dry run for the same call predicts
`["first_name"]` alone. The rehearsal under-reports rather than
over-promising and the guard is unaffected —
`docs/architecture.md`, "The upstream may change more than you asked
for", says why.

## Not covered

- **Claude Desktop.** The surface was driven through stdio and through
  this Claude Code session, not through Desktop. The runbook accepts
  either; a Desktop pass is worth doing before announcing.
- **Integration suite.** No `//go:build integration` files ship yet, so
  the sandbox integration gate is still satisfied by these manual probes
  rather than by `go test -tags=integration`.
- **A second workspace.** Everything here ran against one. A
  custom-field or permission setup unlike that one is untested ground.
