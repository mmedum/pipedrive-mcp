## One assertion was wrong before the server was

`refresh_field_cache` first read as a failure. It was not: the tool
succeeded and refreshed all three resources, and the check asserted
`errors == 0` against a field that is `omitempty` and therefore absent
when zero. `None != 0`, so a working tool was called broken.

Recorded because it is the same shape as the defects this release's
tests were written to remove — an assertion that does not match the
contract it claims to check — and because the first instinct on a red
smoke is to look at the server.

# Post-tag verification — v0.4.0, read rather than watched

**Date:** 2026-09-18
**Tag:** `v0.4.0` at `25ab15e`, annotated (no GPG key is configured on
this machine; `docs/release.md` says tag signing is optional because
cosign covers artifact provenance).
**Workflow:** green — `Build, sign, publish archives` and
`registry / publish`, the latter reached through `workflow_call`.

Green is not the evidence. Each check below was run from outside CI and
paired with a negative that must fail, because a verification that
cannot fail is the defect this release spent the day removing.

## The checksum signature

```
cosign verify-blob SHA256SUMS --bundle SHA256SUMS.bundle
  identity ^…/release.yml@refs/tags/v0\.4\.0$   -> Verified OK, exit 0
  identity ^…/release.yml@refs/tags/v0\.3\.2$   -> exit 1
  SHA256SUMS with one byte appended              -> exit 1
```

The wrong-identity run is the one that matters: it proves the check is
reading the certificate rather than merely finding a well-formed bundle.

## The provenance attestation

`gh attestation verify` prints nothing on success, so exit status is the
whole signal — and a piped exit code reports the pipe, not `gh`. Run
unpiped:

```
pipedrive-mcp-0.4.0.mcpb        -> exit 0
  + one appended byte           -> exit 1
SHA256SUMS                      -> exit 0
  + one appended byte           -> exit 1
```

The bundle verifies **directly**, not only through its checksum row.
That is new in this release: the `.mcpb` was not a `subject-path` until
`#65`, and `gh attestation verify` against it previously answered "no
attestation found" — for the one artifact most people install without
opening a terminal.

## The hash chain

```
sha256sum pipedrive-mcp-0.4.0.mcpb   535e42e9…f97a29f0
SHA256SUMS row for that file          535e42e9…f97a29f0
registry fileSha256 (live API)        535e42e9…f97a29f0
```

Read back from `registry.modelcontextprotocol.io`:
`io.github.mmedum/pipedrive-mcp`, version `0.4.0`, `registryType: mcpb`,
transport `stdio`, identifier pointing at the v0.4.0 release asset.

## The fix that shipped in this release, exercised on its first run

`#64` added a `cosign verify-blob` of `SHA256SUMS` to the publish job,
before `registry-publish` lifts the bundle's hash out of it. Timestamps
from the run confirm the order rather than the intent:

```
09:10:40.5015  cosign verify-blob dist/SHA256SUMS
09:10:40.9638  Verified OK
09:10:40.9668  go run ./scripts/gates registry-publish …
```

So the number now in a registry that cannot retract entries came from a
file whose signature was checked first. Before `#64` it did not.
