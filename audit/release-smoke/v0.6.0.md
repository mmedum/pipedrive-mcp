## Eval baseline, three runs

12 tasks per run, ~$1.55 each.

| Task | Runs passed |
| --- | --- |
| `refuse-the-overwrite` | **0 / 3** |
| `archiving-is-not-closing` | 2 / 3 |
| the other ten | 3 / 3 |

Four tasks report a half nobody could check — they are reads, so there
is no end state to read back, and they say so rather than quietly
scoring nothing.

No run reported workspace drift, a failed fixture reset, or a record
left behind.

**`refuse-the-overwrite` failing 3/3 is a finding, not a flake.** The
model hits the overwrite guard, reads the refusal — which names
`overwrite` as the argument that would permit the write, because a
refusal the caller cannot act on is a bug — and re-sends with it set.
The server is correct: the live guard probes pass, and the refusal is
issued every time. This release rewrote the field description to say a
refusal is NOT a retry signal, and **that did not change the outcome**.
A description raises the cost of routing around a guard; it does not
prevent it. Making it actually hold would mean `overwrite` carrying
something a model cannot mint on its own — echoing back the exact field
list the refusal named — which is a schema change and a semver event,
and has not been decided.

`archiving-is-not-closing` failing once in three is ordinary model
variance on a task that exists to catch exactly that confusion.

## What this release's evals found

`manage_deal` `reopen` had failed against the real API since it shipped,
through v0.4.0 and v0.5.0. It sent `lost_reason: ""` alongside
`status: open`; Pipedrive accepts `lost_reason` only on a deal that is
lost and validates the resulting state, so every reopen was rejected.

No unit test could have caught it — the fakes accept any request, so a
test could only confirm the code sent what the code sent, and one did
exactly that while asserting the broken shape as correct. A live probe
now covers reopen from won and from lost.

## Claude Desktop smoke: not done

Open across four releases now (v0.4.0, v0.5.0, and this one; v0.1.0
predates the requirement). The maintainer was asked before tagging and
chose to ship without it.

The stdio path is exercised thoroughly — `make smoke` on the built
binary, the live integration suite over the server the binary builds,
and three model-driven eval runs. What none of those reach is the
`.mcpb` bundle path: the generated launcher, and keyring access from a
GUI-launched process. This release changes that path only through the
`go-sdk` bump, so the untested surface is no larger than at v0.5.0 —
but it is not smaller either, and this release adds deletes.
