# Security review — v0.4.0

**Date:** 2026-09-17
**Scope:** cumulative diff from `v0.3.2` (`af71b08`) to the v0.4.0
release-prep HEAD on `align/google-mcp-standard` — 47 files,
~5,300+/~820-.
**Reviewer:** `/security-review` skill (general-purpose subagent), run
**twice**: once mid-branch, and again after roughly half the code had
been rewritten in response.

## Result

**Two high-confidence findings in the first pass, both fixed. Second
pass clean.**

## First pass — two findings, both authorization-logic bypass

Both were the same defect in two places: **a field the write path sends
that the resource's `fieldSpec` table does not describe.** The table is
what `changedFields` and `requireOverwrite` walk, so an untabled field is
written without being guarded and without appearing in the `changed`
report — while the tool description promises to refuse over any populated
field and name each one.

1. **`internal/tools/activities.go` — activity `participants`.** Absent
   from `activityFields` entirely while `activityRequestFor` sent it, and
   an update REPLACES that collection. Riding along on an unrelated edit
   it silently deleted every existing attendee; a participants-only
   update looked like a no-op and echoed the stale list back as current.
2. **`internal/tools/guard.go` — person `emails` / `phones`.** Tabled,
   but projected to the primary entry's value alone. That answers "does
   this person have an email", which is the wrong question: the
   destructive case is the primary surviving while the others are
   deleted — exactly what an update sending back only the edited entry
   does.

A third instance of the same root cause was found afterwards by the
`/simplify` altitude pass and is recorded here because it belongs to the
same defect class: `projectContactPoints` rendered only each entry's
value, so re-flagging the primary and relabeling projected identically,
the write was skipped as a no-op, and the caller was told the record was
already in the requested state.

### Fix

The rule is stated once, in `projectCollection`: a collection's render
must cover **every field of the element a write can set**. Both
collections are written against it, and free-text fields are quoted so
two distinct collections cannot render identically.

Three tests pin it rather than trusting it, each verified to fail against
the code it replaced:

- every field an `Update*Request` or `Create*Request` can send has a
  table entry;
- setting any single request field reaches the `changed` report — the
  only assertion covering the overlay, which nothing else pinned;
- every sub-field of a collection element is rendered by its projection.

## Second pass — clean

No HIGH or MEDIUM findings at confidence >= 0.7 over the rewritten code
(`guardedWrite[T]`, the rewritten projections, the `deref`/`ptr`/`clone`
generics, `resolvedX`, the memoized `WhoAmI`, the annotation change).

Verified explicitly:

- No path reaches `Put` without `requireOverwrite` having run.
  `guardedWrite.run` is straight-line, every early exit is a `return`,
  and the five `c.Update*` calls occur only inside a `Put:` closure — so
  `run` is the sole route to an upstream PATCH/PUT.
- The dry-run floor cannot be cleared from the wire: each handler ORs
  `PIPEDRIVE_DRY_RUN` in before branching.
- `Overwrite: in.Overwrite || in.Action != "update"` cannot smuggle a
  free-form update through. Both call sites sit after `validateAction`
  closes the enum and after `create` is routed elsewhere, and the
  transition builders construct narrow bodies from literals, dropping
  every descriptive field the caller also sent.
- The no-op early return fails **closed** — the write is skipped, never
  waved through.
- `sync.Once` establishes happens-before for the `WhoAmI` memo; no race,
  and no cross-principal leakage (one process, one token, one user).
- `resolvedX` shared with the resource templates exposes strictly the
  same fields as the matching `get_` tool, and less for activities.

## Accepted with rationale

Two items the second pass listed as hardening rather than
vulnerabilities were **fixed anyway**, because both are the shape that
had already bitten three times on this branch:

- Unescaped separators in `projectContactPoints` let a crafted label
  absorb the next entry, making two different collections render
  identically. Both free-text fields are quoted now.
- `manage_note`'s `switch` sent its `default` to the destructive branch,
  so a fifth action added to `allowedNoteActions` would silently have
  become a soft delete. `delete` is named; the default errors.

## Standing acceptances

- **Malicious LLM tool selection** remains out of scope, as in prior
  releases. The mitigation is unchanged in kind but stronger in degree:
  `PIPEDRIVE_DRY_RUN` is now a floor every write honors rather than a
  flag covering only some tools.
- **`PIPEDRIVE_ENABLE_DESTRUCTIVE` retired.** Reviewed and cleared as
  not an authorization bypass: nothing destructive reaches the upstream
  without passing the call-time guard, and the only delete is a v1 soft
  delete. Rationale in `CHANGELOG.md` and `docs/security.md`.

# Second review — the range the first one did not cover

**Date:** 2026-09-17
**Scope:** `970bc48..a217221`, the part of v0.4.0 that reached the tag
after the first review ran — 47 files, ~4,650+/~282-. The first review
above was scoped to `v0.3.2..970bc48` on `align/google-mcp-standard`,
and 0.4.0 subsequently absorbed the Claude Desktop bundle and registry
publish, the bundle-manifest conformance work, a CI gate fix,
`internal/app` and the live integration suite. A review whose scope no
longer matches the release is not evidence, which is why this exists
rather than the first one being re-dated.
**Reviewer:** `/security-review` skill (general-purpose subagent).

## Result

**One MEDIUM finding, fixed. No HIGH findings.**

### MEDIUM — the hash published to the MCP registry was never checked
against the signature covering it

`publish-mcp.yml` downloaded `SHA256SUMS` from the published release and
fed it straight into `gates registry-publish`, which lifts the `.mcpb`
row out of it and writes it as the registry entry's `fileSha256`.
Nothing verified that file. `SHA256SUMS.bundle` — the cosign signature
goreleaser produces over exactly this artifact — was never downloaded,
and the `cosign verify-blob` in the workflow ran only against the
`mcp-publisher` tarball. The workflow's own header asserted that "the
hash a client verifies is the number cosign signed"; nothing enforced
it.

The attack needs `contents: write`: replace the `.mcpb` release asset,
edit `SHA256SUMS` to carry its digest. The signature and the build
attestation both break — which is the detection this pipeline exists to
provide — but neither was consulted on the registry path, so a
`workflow_dispatch` re-publish would write the attacker's digest into
the registry as authoritative. Clients driven by the registry then
verify a trojaned bundle against the attacker's own hash and report
success.

Weight: a registry entry cannot be withdrawn, and this path had never
run.

**Fixed** before tagging: the job now downloads `SHA256SUMS*` and runs
`cosign verify-blob` against the bundle, with the certificate identity
pinned to this repository's `release.yml` on a tag ref, before
`registry-publish` reads the file.

### Advisory — a redaction comment that claimed more than it delivered

`internal/app/app.go` said the unexported token plus `LogValue` meant
"neither `slog.Any` nor `%+v` can put a keyring token in a log line".
The `slog` half was true and tested. The `%+v` half was not: `fmt` reads
unexported fields by reflection, and `Settings` implemented no
`Stringer`. Confirmed empirically — `%+v` rendered
`token:<the real token>`. No call site did it, which is why it would
have gone unnoticed until one did.

**Fixed** by making the claim true rather than narrowing it: `Settings`
now implements `String()` delegating to the same redaction, and the test
asserts `%v`, `%+v` and `%s` alongside the slog path. Verified to fail
without it.

## Checked and not flagged

- **The token's path**, keyring → `Settings.token` (unexported) →
  `pipedrive.New` → the `x-api-token` request header. Never a query
  parameter, so a logged URL carries nothing; no error string in
  `internal/credentials` interpolates it.
- **Live-suite data leakage.** The suite asserts on shapes and counts,
  never content; the only values it writes are its own probe markers and
  an RFC 2606 reserved address. Client logs go to `io.Discard`. Nothing
  in it writes to a committed artifact.
- **`mcpbpack.go` archive handling.** It writes a zip and never extracts
  one, so zip-slip does not apply; entry names come from a static table
  rather than the filesystem; globs hard-fail on zero or multiple
  matches. The manifest is re-encoded through a JSON decode/encode, so
  the version string cannot inject a quote.
- **`mcp-publisher` execution.** Downloaded to a file rather than piped
  into `tar`, verified with cosign against a pinned upstream identity
  and the GitHub OIDC issuer before a single named member is extracted
  and run. Permissions are minimal: `contents: read` at workflow level,
  `id-token: write` only on the publish job, `persist-credentials:
  false` on checkout, no inherited secrets.
- **`merge-base.sh` and the `ci.yml` gate changes.** The interpolated
  base ref must name a branch in the base repository, which a fork
  contributor cannot create; `ci.yml` uses `pull_request`, not
  `pull_request_target`, with `contents: read` and no secrets.

## Known and not fixed here

`dist/*.mcpb` is not a `subject-path` on the provenance attestation in
`release.yml`; it is covered transitively through `SHA256SUMS`, which is
now verified on the publish path. Attesting the bundle directly would be
strictly better and is a change to the release workflow rather than to
the publish one.
