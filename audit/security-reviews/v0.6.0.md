# Security review — v0.6.0 release boundary

**Date:** 2026-09-19 (reviewed), release cut 2026-09-21
**Range reviewed:** `v0.5.0..HEAD` at review time (`main`, post-#85)
**Diff:** 51 files, +3194/−186
**Posture:** release-boundary review. High-confidence, exploitable
findings only (confidence ≥ 8). DoS/resource exhaustion, secrets at
rest, rate limiting, theoretical races, dependency currency, generic
missing hardening and test-only files were out of scope by instruction.

## Verdict

**Clean. No HIGH or MEDIUM finding reached the reporting bar.**

The two largest new attack surfaces in this range — a delete capability
on four resources, and a harness that shells out to another process —
were traced end to end and cleared. Two sub-threshold observations were
recorded rather than filed, and **both were acted on anyway**; one of
them turned out to matter more than its score suggested.

## What was traced and cleared

**Information disclosure on the new error paths.** `classifyResponse`
now reports a non-JSON body as `non-JSON response (N bytes)`. Only
`len(raw)` reaches the string — the body is never formatted, stored or
logged — and the field is set only when the upstream envelope yielded no
message, so it cannot displace or concatenate with upstream text. The
partial-unmarshal case (a body that populates `error` *and* errors) was
checked explicitly: the upstream message wins and the length note is
discarded. `withV1Sunset` appends a package constant with nothing
interpolated. What reaches the model is `APIError.Message` alone — not
`Endpoint`, not `Status`, not the body — and `pathOf` strips query and
host before `Endpoint` is set, so the `x-api-token` header is
unreachable even through `APIError.Error()`.

**The delete capability.** All four paths run `validatePositiveID` (so
the id cannot manipulate a path segment — it is rendered with
`strconv.FormatInt` into a fixed shape), then a read, then
`checkExpectVersion`, then `if !in.DryRun` around the only client call.
The dry-run floor is applied before dispatch, so it covers delete
identically to update and create and a per-call `dry_run: false` cannot
clear it. `delete` is not a transition, so it does not leak into
`SelfAuthorizingActions()` and does not become overwrite-exempt.
`shouldRetry` retries 429 only, so a DELETE is never replayed on 5xx.

**Command and argument injection in `scripts/evals`.** Every value
reaching a prompt is locally invented or a numeric id, so no
API-returned string — an attacker-controlled organization name included
— reaches argv or a path. Even if one did: `exec.CommandContext` uses no
shell, the prompt occupies the value slot of `-p`, and the subprocess is
bounded by `--strict-mcp-config`, an allow-list of `mcp__pipedrive__*`
and an explicit `--disallowed-tools`.

**Temp file handling.** `os.CreateTemp` — unpredictable name, `O_EXCL`,
mode 0600, deferred removal, contents just a path.

**The protocol upgrade.** `2026-07-28` support comes entirely from the
SDK bump; no non-test change in `internal/server/` or `cmd/`. Transport
is stdio only and credentials come from the keyring or environment at
process start, never from the protocol, so serving the stateless
revision beside the legacy handshake introduces no session or auth
surface — there is no session-scoped authority to confuse.

Also cleared: the two new gates (local file reads, no shell, no
network), the CI schema-diff range change, and the stream parser.

## Sub-threshold observations, and what was done about them

Neither was filed as a finding. Both were fixed.

**1. `make descriptions` wrote to a fixed `/tmp` path** (~6 confidence:
mechanism certain, exploitability needs a hostile local user, and CI
runners are single-user). The dump is now piped to the gate on stdin, so
there is no file and nothing to pre-plant as a symlink.

**2. The eval census counted one page capped at 100, and
`maxListLimit` is 100.** Scored below the bar because it is a
correctness issue rather than a vulnerability — but it meant the drift
check advertised as catching a stray row in a real CRM returned the same
saturated number on both sides of every run on any workspace with 100+
records, and reported no drift without having looked. **No test could
have caught it: a saturated count is a plausible number, not an error.**
It was replaced wholesale — the check now lists what each resource
reports as updated since the run began and subtracts the fixture's own
ids, which is the question that was actually being asked and is
independent of workspace size.

The second is the useful lesson from this review. The finding that
mattered most was the one that scored lowest, because it was not a
vulnerability at all — it was a guard that had stopped guarding while
continuing to report success.
